# Migration guide: 4.2.0

This guide applies when you upgrade to 4.2.0, or to a 4.2.0 release candidate after 4.2.0-rc2, from one of these releases:

- 4.1.x.
- 4.2.0-rc1 or 4.2.0-rc2.

The [GitHub release](https://github.com/Saremox/redis-operator/releases) lists all the changes. Steps 19 and 20 tell how to downgrade to 4.1.x.

## Before the upgrade

### 1. Find the RedisFailovers that will restart

With a custom pod `securityContext` and no `seccompProfile`, a RedisFailover keeps the `RuntimeDefault` seccomp profile (#230). The operators of 4.2.0-rc2 and older removed the default profile from these pods. The profile changes the pod template, so the redis and sentinel pods restart one time.

The default soft pod anti-affinity does not select on the `redisfailovers-role` label (#248). The 4.1.x selector included this label. The master has a different value of it, so the scheduler did not count the master. A replica could then go to the node of the master. This change restarts the redis pods of each RedisFailover without `spec.redis.affinity`.

The redis pods mount no ServiceAccount token when `spec.redis.serviceAccountName` is empty. The sentinel pods mount no token when `spec.sentinel.serviceAccountName` is empty. The generated containers do not use the Kubernetes API. This change restarts the affected pods one time. A pod with a `serviceAccountName` keeps the token mount.

The default probes are also part of the pod template. The redis pods restart one time when the RedisFailover sets no `redis.customLivenessProbe` (#217, #249). With Sentinel enabled, the sentinel pods restart one time when the RedisFailover sets no `sentinel.customLivenessProbe` or no `sentinel.customReadinessProbe` (#217, #218).

1. List the affected RedisFailovers:

   ```shell
   kubectl get redisfailovers -A -o json | jq -r '.items[]
     | select(
         (.spec.redis.affinity == null)
         or (.spec.redis.securityContext != null and .spec.redis.securityContext.seccompProfile == null)
         or (.spec.sentinel.securityContext != null and .spec.sentinel.securityContext.seccompProfile == null)
         or .spec.redis.customLivenessProbe == null
         or (.spec.redis.serviceAccountName // "") == ""
         or (.spec.sentinel.enabled == true and (.spec.sentinel.serviceAccountName // "") == "")
         or (.spec.sentinel.enabled == true
           and (.spec.sentinel.customLivenessProbe == null or .spec.sentinel.customReadinessProbe == null)))
     | "\(.metadata.namespace)/\(.metadata.name)"'
   ```

2. Plan the upgrade for a time when one failover is acceptable for each of these RedisFailovers. The operator replaces the redis replicas first, one at a time, and waits until each replacement pod is ready. It replaces the master last:
   - With Sentinel, the operator waits until each Sentinel sees a quorum of replicas. The replacement of the master then starts a Sentinel failover.
   - Without Sentinel, the operator sends `FAILOVER` to the master (#274). A synced replica becomes master, and then the operator deletes the pod that was master. With one Redis pod, without `FAILOVER` (Redis before 6.2 or a rename), or after 3 refusals, the operator deletes the master pod without a handover. Then the operator elects a master after that pod stops. Writes fail until then.
   - In bootstrap mode, only the replicas restart.

   The metric `redis_operator_controller_redis_checks_total` counts an aborted handover with the indicator `MASTER_HANDOVER_ABORTED` and the status `UNHEALTHY`. The operator then tries the handover again. Kubernetes replaces the sentinel pods with the `RollingUpdate` strategy. These changes restart a pod only one time.
3. If a workload cannot run with `RuntimeDefault`, set `seccompProfile` in the `securityContext` of that RedisFailover before the upgrade.

### 2. Remove the command renames that validation rejects

The operator does not reconcile a RedisFailover with a rename of a command that it needs (#248). The status shows `NotHealthy` and the validation error. Without reconciliation, the operator does not move the master label and does not repair a failed master. These renames already broke the RedisFailover, except `ACL` without an `aclfile` and `SAVE`, which validation allows.

1. List the RedisFailovers with such a rename:

   ```shell
   kubectl get redisfailovers -A -o json | jq -r '.items[] | . as $rf
     | select(any(.spec.redis.customCommandRenames[]?.from | ascii_upcase;
         IN("AUTH", "CLIENT", "CONFIG", "INFO", "PING", "PSYNC", "REPLCONF", "REPLICAOF", "SLAVEOF")
         or (. == "ACL" and any($rf.spec.redis.customConfig[]?; ascii_downcase | startswith("aclfile")))
         or (IN("EXEC", "MULTI", "PUBLISH", "SUBSCRIBE") and $rf.spec.sentinel.enabled == true
           and ($rf.spec.bootstrapNode == null or $rf.spec.bootstrapNode.allowSentinels == true))))
     | "\($rf.metadata.namespace)/\($rf.metadata.name)"'
   ```

2. Remove these entries from `spec.redis.customCommandRenames` of each listed RedisFailover. Redis reads `rename-command` only at startup, so the change applies at the next restart of a pod.

### 3. Copy the objects that the operator deletes

The operator deletes the PodDisruptionBudget `rfr-<NAME>` or `rfs-<NAME>` when `disablePodDisruptionBudget` is `true` (#248). A PodDisruptionBudget that stays blocks the node drains that the flag must permit. The operator also deletes the ServiceAccount `rfs-sa-<NAME>` when `sentinel.serviceAccountName` names a different ServiceAccount, and no Sentinel pod uses it. The operator deletes only an object that the RedisFailover owns.

1. If you use one of these objects, copy it under a different name before the upgrade.

### 4. Update a ClusterRole that you maintain yourself

The operator writes the RedisFailover status through the `status` subresource (#207). This needs `get` and `patch` on `redisfailovers/status`. Without these verbs, the API server refuses each status write.

The ClusterRoles in the Helm chart, in `manifests/kustomize` and in `example/operator` grant these verbs. If you use one of them, go to the next step.

1. Add this rule to your ClusterRole:

   ```yaml
   - apiGroups:
       - databases.spotahome.com
     resources:
       - redisfailovers/status
     verbs:
       - get
       - patch
   ```

2. Optionally, add `delete` on `poddisruptionbudgets` and `serviceaccounts`. Without this verb, the operator logs a warning and keeps the objects from step 3.
3. Optionally, add `patch` on `pods/resize`, and `get` on `controllerrevisions` in the `apps` group (#191). Without these verbs, the operator recreates a pod that it can resize in place.
4. Optionally, add `list` and `watch` on `secrets` if you set `--watch-auth-secrets` (#212). These verbs can read every Secret in the cluster.
5. With the Helm chart, set `watchAuthSecrets: true` instead of the flag in `image.cli_args`. The value sets the flag and grants the verbs.
6. Add `create` and `update` on `secrets` (#287). The operator keeps the passwords that the Redis pods run with in a Secret. These verbs can change every Secret in the cluster. Without these verbs, the operator logs a warning, and a restart during a password change can stop the change.
7. Apply the ClusterRole before you upgrade the operator.

### 5. Set the image pull Secrets of the Helm chart

Do this step only if you install with Helm and set `imageCredentials.create: true`.

The default of `imageCredentials.existsSecrets` is `[]` (#244). With an empty list, the chart creates a pull Secret from `imageCredentials.registry`, `username` and `password`. If `username` or `password` has the placeholder value, `helm upgrade` stops with an error.

1. If the operator pod pulls with the Secret `registrysecret`, add it to your values:

   ```yaml
   imageCredentials:
     create: true
     existsSecrets:
       - registrysecret
   ```

2. If you want a pull Secret from the chart, set `imageCredentials.registry`, `imageCredentials.username` and `imageCredentials.password`.

### 6. Prepare an install with kubectl or kustomize

Do this step only if you install with `redis-operator.yaml`, a kustomize overlay or `example/operator`.

The `redis-operator.yaml` file contains the `overlays/default` overlay (#244). The overlays install the operator in the `default` namespace. The ClusterRoleBinding must name the namespace of the ServiceAccount, so the files cannot leave the namespace open.

- `kubectl apply -n <namespace>` does not work with these files. kubectl refuses the namespaced objects, but it applies the ClusterRole and the ClusterRoleBinding.
- The Deployment of `redis-operator.yaml` has a different selector than the file of 4.2.0-rc2 and older. Kubernetes cannot change the selector of a Deployment, so you must delete the Deployment of the current install.
- Run only one operator in a cluster. Each operator takes the leader lease in its own namespace, so two operators in different namespaces both change the RedisFailovers.
- `redis-operator.yaml` and the overlays contain the CRD, which is larger than 1 MB. A client-side `kubectl apply` fails on it, because the limit for the annotations of an object is 256 KiB. Apply these files server-side, also with your own `namespace:`.
- `example/operator/all-redis-operator-resources.yaml` has no CRD. Its Deployment `redisoperator` keeps its selector, so you do not delete it.

1. To install the operator in a namespace other than `default`, write a `kustomization.yaml`:

   ```yaml
   apiVersion: kustomize.config.k8s.io/v1beta1
   kind: Kustomization

   namespace: <namespace>

   resources:
     - github.com/Saremox/redis-operator/manifests/kustomize/overlays/default?ref=<release-tag>
   ```

2. For `redis-operator.yaml` or a change of the namespace, delete the operator Deployment of the current install in step 16:

   ```shell
   kubectl delete deployment redis-operator -n <current-namespace>
   ```

3. In step 16, apply `redis-operator.yaml` or your `kustomization.yaml` server-side:

   ```shell
   kubectl apply --server-side -f redis-operator.yaml
   kubectl apply --server-side -k <directory>
   ```

4. If you install with `example/operator`, apply the file of the same release in step 16:

   ```shell
   kubectl apply -f https://raw.githubusercontent.com/Saremox/redis-operator/${REDIS_OPERATOR_VERSION}/example/operator/all-redis-operator-resources.yaml
   ```

### 7. Find the RedisFailovers that get the Sentinel timeouts of the operator

The operator adds `down-after-milliseconds 5000` and `failover-timeout 10000` to the Sentinel `customConfig` when `customConfig` does not set them (#242). The operators of 4.2.0-rc2 and older added them only to an empty `customConfig`. With other entries, a restarted Sentinel used `1000` and `3000` from `sentinel.conf`. After the operator monitored the master again, the Sentinel used the built-in values `30000` and `180000`.

The operator applies `5000` and `10000` to the Sentinels at the next reconcile after the upgrade. The pods do not restart. Sentinel then marks the master as down after 5 seconds without an answer, not after 30 seconds.

1. List the affected RedisFailovers:

   ```shell
   kubectl get redisfailovers -A -o json | jq -r '.items[]
     | select(.spec.sentinel.enabled == true and (.spec.sentinel.customConfig // []) != [])
     | [.spec.sentinel.customConfig[] | split(" ")[0] | ascii_downcase] as $keys
     | select(($keys | index("down-after-milliseconds")) == null or ($keys | index("failover-timeout")) == null)
     | "\(.metadata.namespace)/\(.metadata.name)"'
   ```

2. To keep the built-in values, add `down-after-milliseconds 30000` and `failover-timeout 180000` to `spec.sentinel.customConfig` before the upgrade. In most cases, the Sentinels already use these values, so the change has no effect before the upgrade.

If the list is empty, or `5000` and `10000` are correct for you, go to the next step.

### 8. Remove the shell from an operator Deployment that you maintain yourself

Do this step only if you maintain the operator Deployment yourself. Also do it if you patch the Deployment of the chart or of the overlays.

The operator image is distroless (#251). It has no shell and no package manager.

1. Remove each shell command, for example `sh -c`, from the operator container.
2. Replace each `exec` probe with a `tcpSocket` probe on the metrics port, as in the Helm chart.
3. To debug the operator pod, use `kubectl debug`.

### 9. Update the operator arguments and the chart values

The chart reads `image.cli_args` as a list, and splits a string at whitespace (#244). It sets `--listen-address` from `container.port`, because the probes and the Services use this port. A second `--listen-address` in `image.cli_args` can make the operator listen on a port that the probes do not use.

With `serviceAccount.create: true`, the chart creates the ServiceAccount that `serviceAccount.name` names (#223). `helm upgrade` refuses to change an object that the release does not own.

The metrics port serves `/debug/pprof/` only with `--enable-pprof` (#253).

1. With the Helm chart, remove `--listen-address` from `image.cli_args`.
2. Set the port in `container.port`.
3. With `serviceAccount.create: true`, check whether you created the ServiceAccount of `serviceAccount.name` yourself.
4. If you created it yourself, delete it immediately before step 16. The chart then creates it again. Step 20 tells how to downgrade in this case.
5. As an alternative, set `serviceAccount.create: false`. The chart then creates no ServiceAccount and no RBAC objects for the operator, so you must give the operator its permissions.
6. To use the profiler, add `--enable-pprof` to the arguments of the operator. With the Helm chart, the arguments are in `image.cli_args`.

### 10. Update the scrape configuration and the alerts

The Service `rfr-<NAME>` has the port number of the exporter in `prometheus.io/port` (#260). A Prometheus scrape configuration that reads this annotation can then reach the exporter. A ServiceMonitor that also scrapes the exporter gives each series two times.

1. If a ServiceMonitor scrapes the exporter of a RedisFailover, set `prometheus.io/scrape: "false"` in `spec.redis.serviceAnnotations`.
2. If you install with `example/operator`, delete its PodMonitor after step 16. `kubectl apply` does not delete it:

   ```shell
   kubectl delete podmonitor redisoperator -n default
   ```

3. Change dashboards and alerts that select a Secret or a ConfigMap by the `name` label of `redis_operator_controller_k8s_operations_total` (#264).
4. Make sure that alerts on `status.state` accept a `NotHealthy` state of some seconds (#213, #243, #278).
5. Change dashboards and alerts that select a redis or sentinel pod by its IP:
   - In `redis_operator_controller_redis_operations_total`, use the labels `namespace` and `pod_name` instead of `IP`.
   - In `redis_operator_controller_redis_checks_total` and `redis_operator_controller_sentinel_checks_total`, use the label `pod_name` instead of `instance`. Its value is the pod name, or `NA` for a check of the RedisFailover.

   A pod IP changes each time Kubernetes creates the pod again. A redis pod keeps its name, so its series continue. A sentinel pod gets a different name, and its series change. When the operator does not know the pod of an IP, `pod_name` has the IP and `namespace` has `NA`. With the host network, two redis pods or two sentinel pods can have the IP of one node. In this case, they also get the IP as `pod_name`. The dashboard in `example/grafana-dashboard` uses the pod names.

   The name `pod_name` does not collide with the target labels `instance` and `pod` that Prometheus and a ServiceMonitor add. These metrics do not have the label `instance` or `exported_instance`.

   The operation `SET_SENTINEL_TO_MONITOR_REDIS_WITH_GIVEN_PORT` has the kind `SENTINEL`, not `REDIS`, because the operator sends it to a Sentinel.

### 11. Find the RedisFailovers with Sentinel and Redis before 6.2

With Sentinel, the shutdown script of the master pauses the writes with `CLIENT PAUSE WRITE`. It waits at most 6 seconds until the online replicas confirm all writes, then asks Sentinel for a failover. Redis before 6.2 does not have `CLIENT PAUSE WRITE`. A failover without the pause loses writes, so the script asks for no failover (#254). Sentinel then fails over after `down-after-milliseconds`, and writes fail until then.

The pause also fails after a password change, until the pod restarts. The variable `REDIS_PASSWORD` of the pod keeps the password from the start of the pod, and Redis refuses it. Thus, when a password change restarts the master pod, writes fail until Sentinel fails over after `down-after-milliseconds`.

1. List the RedisFailovers with Sentinel and their Redis image:

   ```shell
   kubectl get redisfailovers -A -o json | jq -r '.items[]
     | select(.spec.sentinel.enabled == true
         and (.spec.bootstrapNode == null or .spec.bootstrapNode.allowSentinels == true))
     | "\(.metadata.namespace)/\(.metadata.name) \(.spec.redis.image // "default")"'
   ```

2. For each image with Redis before 6.2, set `spec.redis.image` to Redis 6.2 or later. The default image has Redis 7.2. A change of the image restarts the redis pods.
3. Plan each password change for a time when a write outage of `down-after-milliseconds` is acceptable.

### 12. Check the custom shutdown scripts

Do this step only if a RedisFailover sets `spec.redis.shutdownConfigMap`.

The redis pods have no service-link variables, so `RFS_<NAME>_SERVICE_HOST` and `RFS_<NAME>_SERVICE_PORT_SENTINEL` are empty. This is also true for 4.1.x, but the example script of 4.1.x reads these variables. A script that reads them cannot reach Sentinel and asks for no failover. Sentinel then fails over after `down-after-milliseconds`, and writes fail until then.

The default script finds Sentinel through the Service `rfs-<NAME>` on port 26379 (#229). It pauses the writes before it asks for the failover, so that the old master acknowledges no write after the promotion. Sentinel promotes the replica with the highest replication offset that it knows, but this offset can be 10 seconds old. Thus the script also waits until each online replica confirms the `master_repl_offset` of the master. The wait ends at the latest 6 seconds after the start of the script.

1. List the RedisFailovers with a custom shutdown script:

   ```shell
   kubectl get redisfailovers -A -o json | jq -r '.items[]
     | select((.spec.redis.shutdownConfigMap // "") != "")
     | "\(.metadata.namespace) \(.metadata.name) \(.spec.redis.shutdownConfigMap)"'
   ```

2. For each ConfigMap, find the lines that read the service-link variables:

   ```shell
   kubectl get configmap <configmap> -n <namespace> -o jsonpath='{.data.shutdown\.sh}' | grep -n 'RFS_'
   ```

3. In these scripts, use the host `rfs-<NAME>` and the port `26379`.
4. Pause the writes with `CLIENT PAUSE <milliseconds> WRITE` before `SENTINEL FAILOVER`. See `example/redisfailover/custom-shutdown.yaml`.
5. Between the pause and `SENTINEL FAILOVER`, wait until each online replica in `INFO replication` has the `offset` of `master_repl_offset`.

### 13. Check the failover timeout without Sentinel

Do this step only if a RedisFailover runs without Sentinel and without `bootstrapNode`.

The operator waits `spec.sentinel.failoverTimeout` before it replaces a master that does not answer while its pod runs (#213). The default is `10s`. The operators of 4.2.0-rc2 and older do not wait for this time. The wait prevents a failover after a short stall, because a failover makes all replicas resync and can lose writes. During the wait, the state is `NotHealthy`, and `status.message` shows the wait. When the operator finds no master pod, it elects a master at once.

1. List the RedisFailovers without Sentinel and their timeout:

   ```shell
   kubectl get redisfailovers -A -o json | jq -r '.items[]
     | select(.spec.sentinel.enabled != true and .spec.bootstrapNode == null)
     | "\(.metadata.namespace)/\(.metadata.name) \(.spec.sentinel.failoverTimeout // "10s")"'
   ```

2. To disable the wait, set `spec.sentinel.failoverTimeout: 0s`. Also with `0s`, the operator does not replace a master whose pod is ready.

### 14. Check the PVC sizes

Do this step only if a RedisFailover sets `spec.redis.storage.persistentVolumeClaim`.

At each reconcile, the operator increases the storage request of each PVC that is smaller than the request of the RedisFailover (#240). The operators of 4.2.0-rc2 and older resized the PVCs only when the request changed. Thus a PVC that the StatefulSet created after a resize, for example at a scale-up, kept a smaller size. A StorageClass without `allowVolumeExpansion: true` refuses the resize. The operator then logs the warning `resize pvc failed` at each reconcile.

With `keepAfterDeletion: true`, the operator removes the owner reference of the RedisFailover from the PVCs. Kubernetes then keeps the PVCs when you delete the RedisFailover. The operators of 4.2.0-rc2 and older did not remove it when you added `keepAfterDeletion` to a RedisFailover.

1. List the storage request of each RedisFailover:

   ```shell
   kubectl get redisfailovers -A -o json | jq -r '.items[]
     | select(.spec.redis.storage.persistentVolumeClaim != null)
     | "\(.metadata.namespace) \(.metadata.name) \(.spec.redis.storage.persistentVolumeClaim.spec.resources.requests.storage)"'
   ```

2. For each RedisFailover, list the size and the StorageClass of its PVCs:

   ```shell
   kubectl get pvc -n <namespace> -l app.kubernetes.io/component=redis,app.kubernetes.io/name=<name> \
     -o custom-columns='NAME:.metadata.name,REQUEST:.spec.resources.requests.storage,CLASS:.spec.storageClassName'
   ```

3. If a PVC is smaller than the request, make sure that its StorageClass allows volume expansion.

### 15. Prepare for the in-place resize

On Kubernetes 1.33 or later, the operator resizes a redis pod in place when only the CPU or memory of its containers changes (#191). The pod does not restart, so Redis does not reload its data and the master does not fail over. To lower a memory limit in place, Kubernetes 1.35 is necessary. In the other cases, the operator recreates the pod (#204, #261). The [README](../../README.md#in-place-resize) gives the cases.

A ResourceQuota or a LimitRange can reject a resize. The operator then does not recreate the pod, because the same rejection applies to a recreated pod (#276). The rollout holds, and `status.message` starts with `resize of pod <pod> is blocked by a ResourceQuota or LimitRange`. The rollout continues when the quota or the LimitRange allows the resources.

1. Before you change `spec.redis.resources`, make sure that the ResourceQuota and the LimitRange of the namespace allow the values.
2. To always recreate the pods, set `spec.redis.inPlaceResize: Disabled` after step 16. The 4.1.x CRD does not know this field.

## Upgrade

### 16. Replace the CRD and upgrade the operator together

The CRD enables the `status` subresource (#207). An operator and a CRD from different releases cannot write the status:

- The 4.1.x operator writes the status through the main resource. The API server ignores these writes with the 4.2.0 CRD.
- The 4.2.0 operator writes the status through the `status` subresource. These writes fail with the 4.1.x CRD.

The RedisFailovers keep their current status during the upgrade. Do step 16 in one maintenance window, so the time between the CRD and the operator upgrade is short.

Helm does not update the CRD on `helm upgrade`. It installs the CRD only on `helm install`.

1. Set the version:

   ```shell
   REDIS_OPERATOR_VERSION=<release-tag>
   ```

2. Replace the CRD:

   ```shell
   kubectl replace -f https://raw.githubusercontent.com/Saremox/redis-operator/${REDIS_OPERATOR_VERSION}/manifests/databases.spotahome.com_redisfailovers.yaml
   ```

   If you set `crds.upgradeHook.enabled: true` in the chart values, a Helm hook applies the CRD before the operator upgrade. In that case, do not do this step.

3. Upgrade the operator immediately:

   ```shell
   helm upgrade redis-operator redis-operator/redis-operator --version ${REDIS_OPERATOR_VERSION}
   ```

   If you install with kubectl or kustomize, apply the operator manifests of the same release. Step 6 gives the order.

### 17. Apply the RedisFailovers with the fields of the 4.2.0 CRD again

The API server removes the fields that the CRD schema does not know, and it does not show an error. The 4.2.0 CRD does not restore these fields.

The 4.1.x CRD does not know these fields:

- `redis.env` and `sentinel.env` (#145).
- `redis.exporter.port` and `sentinel.exporter.port` (#144).
- `sentinel.strategy`, `redis.podDisruptionBudgetMinAvailable` and `sentinel.podDisruptionBudgetMinAvailable` (#146).
- `redis.preventMasterEviction` (#147), `redis.maxMemory` (#190) and `redis.inPlaceResize` (#191).
- `redis.autoscaling` (#288). The CRDs of 4.2.0-rc1 and 4.2.0-rc2 also do not know this field.

The CRDs of 4.1.x, 4.2.0-rc1 and 4.2.0-rc2 have the schema of an older k8s.io/api. The 4.2.0 CRD has the schema of k8s.io/api 0.37 (#208). The older CRDs do not know fields such as `httpGet.protocol`, `grpc.mode` and `volumeMounts[].bindMountOptions`.

1. Find the RedisFailover manifests that set one of these fields.
2. Apply these manifests again after step 16.

If no RedisFailover sets one of these fields, go to the next step.

## After the upgrade

### 18. Make sure that the upgrade is correct

1. Make sure that the CRD has the `status` subresource:

   ```shell
   kubectl get crd redisfailovers.databases.spotahome.com \
     -o jsonpath='{.spec.versions[?(@.name=="v1")].subresources}'
   ```

   The output is `{"status":{}}`.

2. Make sure that the operator log has no errors for status writes. An error with `forbidden` and `redisfailovers/status` tells you that a ClusterRole does not have the verbs from step 4.
3. Make sure that each RedisFailover has the state `Healthy` after the pods restart:

   ```shell
   kubectl get redisfailovers -A \
     -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,STATE:.status.state'
   ```

4. Make sure that only one operator Deployment exists. This command lists each Deployment with `redis-operator` in a container image:

   ```shell
   kubectl get deployments -A -o json | jq -r '.items[]
     | select(any(.spec.template.spec.containers[]; .image | contains("redis-operator")))
     | "\(.metadata.namespace)/\(.metadata.name)"'
   ```

5. For each RedisFailover from step 7, make sure that the Sentinels use the timeouts that you expect:

   ```shell
   kubectl exec -n <namespace> deploy/rfs-<name> -c sentinel -- \
     redis-cli -p 26379 SENTINEL MASTER mymaster | grep -A1 -E '^(down-after-milliseconds|failover-timeout)$'
   ```

## Downgrade

### 19. Downgrade with `redis.autoscaling.mode: Auto`

An operator without mode `Auto` rejects a RedisFailover with this mode in validation. It then stops all reconciles of the RedisFailover, also the failover of the operator-managed mode. The 4.1.x CRD also removes `redis.autoscaling` from the stored RedisFailovers. Then the 4.1.x operator gives the pods the limit of `redis.resources`. That limit can be smaller than the memory that Redis holds, and a store can then lose data or refuse writes.

Do these steps for each RedisFailover with `redis.autoscaling.mode: Auto`, before step 20:

1. Read the limit of the pods:

   ```shell
   kubectl get redisfailover <NAME> -n <NAMESPACE> -o jsonpath='{.status.autoscaling.effectiveMemory}'
   ```

2. If the value is empty, go to sub-step 5. The StatefulSet has the limit of `redis.resources`. A pod can still run with a larger limit, for example after a late resize. Such a pod keeps its limit until it restarts.
3. Set `spec.redis.resources.requests.memory` and `spec.redis.resources.limits.memory` to the value.
4. When `status.autoscaling.phase` is `Applying` or `Held`, wait until it is `Done`. The step continues with the spec limit of sub-step 3. Mode `Off` recreates a pod that refuses the limit.
5. Set `spec.redis.autoscaling.mode` to `Recommend` or `Off`.
6. Wait until `status.state` is `Healthy`.

Sub-steps 3 and 5 keep the limit of the pods, because the spec limit is then equal to the effective limit.

With autoscaling, the 4.2.0 operator writes the annotation `redisfailovers.databases.spotahome.com/spec-memory-limit` to the redis StatefulSet. The annotation changes no pod.

### 20. Downgrade to 4.1.x

The 4.1.x operator writes the status through the main resource. The 4.2.0 CRD has the `status` subresource, so the API server ignores these writes. Thus replace the CRD and the operator together, as in step 16.

`helm rollback` does not change the CRD. The CRD upgrade hook of the chart runs only on `helm install` and `helm upgrade`.

The 4.1.x CRD does not know the fields from step 17. The API server removes them from the stored RedisFailovers, for example `redis.autoscaling` and `status.autoscaling`. After a later upgrade, apply these RedisFailovers again.

The 4.1.x operator does not read the Secret `rfr-auth-applied-<NAME>` or the ConfigMap `rfa-<NAME>`. Thus it does not know a password that a pod runs with during a password change. Kubernetes deletes both objects together with the RedisFailover.

The pod templates change again, so the redis and sentinel pods restart one time.

With `serviceAccount.create: true` and `serviceAccount.name`, the 4.1.x chart creates a ServiceAccount with the full name of the release. Its ClusterRoleBinding names only this ServiceAccount, but its Deployment uses the ServiceAccount of `serviceAccount.name`. The 4.2.0 release owns that ServiceAccount (#223), so `helm rollback` deletes it. The operator pod then cannot start until you create the ServiceAccount again.

1. Make sure that each RedisFailover has the state `Healthy`.
2. Do not change an auth Secret until each RedisFailover is `Healthy` on 4.1.x.
3. If you maintain the operator Deployment yourself, remove `--enable-pprof` and `--watch-auth-secrets` from its arguments. The 4.1.x operator does not know these flags and does not start with them.
4. Replace the CRD with the CRD of the 4.1.x release:

   ```shell
   kubectl replace -f https://raw.githubusercontent.com/Saremox/redis-operator/<4.1.x-tag>/manifests/databases.spotahome.com_redisfailovers.yaml
   ```

5. With Helm, run `helm rollback` immediately. `helm history redis-operator` shows the revisions:

   ```shell
   helm rollback redis-operator <revision>
   ```

6. If you set `serviceAccount.name` with `serviceAccount.create: true`, create that ServiceAccount after the rollback:

   ```shell
   kubectl create serviceaccount <serviceAccount.name> -n <operator-namespace>
   ```

7. Bind this ServiceAccount to the ClusterRole of the chart. `kubectl get clusterrole -l app.kubernetes.io/instance=<release-name>` shows the `<full-name>` of the ClusterRole:

   ```shell
   kubectl create clusterrolebinding <full-name>-<serviceAccount.name> --clusterrole=<full-name> \
     --serviceaccount=<operator-namespace>:<serviceAccount.name>
   ```

8. With kubectl or kustomize, immediately delete the operator Deployment.
9. Install the operator of the 4.1.x release as its README tells.
10. Use `example/operator/all-redis-operator-resources.yaml` of that release, or a kustomization with your own `namespace:`. The `redis-operator.yaml` file of 4.1.x has no ServiceAccount and no RBAC.
11. Set the operator image, because the 4.1.x manifests deploy a different image. The [README](../../README.md#install-with-kubectl) tells how.
12. Make sure that each RedisFailover has the state `Healthy` after the pods restart.
