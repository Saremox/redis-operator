# Migration guide: 4.2.0

This guide applies when you upgrade to 4.2.0, or to a 4.2.0 release candidate after 4.2.0-rc2, from one of these releases:

- 4.1.x.
- 4.2.0-rc2 or an earlier 4.2.0 release candidate.

The [GitHub release](https://github.com/Saremox/redis-operator/releases) lists all the changes.

## Summary

| Change | Action |
| --- | --- |
| The CRD enables the `status` subresource (#207). | Replace the CRD and upgrade the operator together. |
| The CRD has the schema of k8s.io/api 0.37 (#208). | Replace the CRD. Then apply the RedisFailovers that use new fields again. |
| The operator writes the status through `redisfailovers/status` (#207). | Add `get` and `patch` on `redisfailovers/status` to a ClusterRole that you maintain yourself. |
| A custom pod `securityContext` keeps the `RuntimeDefault` seccomp profile (#230). | Plan one restart of the affected redis and sentinel pods. |
| The default probes of Redis and Sentinel change (#217, #218, #249). | Plan one restart of the redis and sentinel pods that use a default probe. |
| The chart default of `imageCredentials.existsSecrets` is `[]` (#244). | With `imageCredentials.create: true`, set `existsSecrets` or the registry credentials. |
| `redis-operator.yaml` and the kustomize overlays install the operator in the `default` namespace (#244). | For another namespace, use your own kustomization. Delete the old operator Deployment. |
| A Sentinel `customConfig` without `down-after-milliseconds` or `failover-timeout` gets the operator defaults for them (#242). | To keep the Sentinel built-in timeouts, set them in `customConfig`. |
| The default pod anti-affinity of the redis pods also counts the master (#248). | Plan one restart of the redis pods and one failover. |
| Validation rejects a rename of a command that the RedisFailover needs (#248). | Remove these renames before the upgrade. |
| The operator deletes a disabled PodDisruptionBudget and an unused Sentinel ServiceAccount (#248). | Copy the objects that you use. Optionally, add `delete` to your ClusterRole. |
| The operator serves `/debug/pprof/` only with `--enable-pprof` (#253). | To use the profiler, add `--enable-pprof`. With the Helm chart, add it to `cli_args`. |

## Before the upgrade

### 1. Find the RedisFailovers that will restart

Since #230, a RedisFailover with a custom pod `securityContext` and no `seccompProfile` gets the `RuntimeDefault` seccomp profile. Earlier releases removed the default profile from these pods. The new profile changes the pod template, so the redis and sentinel pods restart one time.

Since #248, the default soft pod anti-affinity does not select on the `redisfailovers-role` label. The master has a different value of this label, so the scheduler did not count it, and a replica could go to the node of the master. This change restarts the redis pods of each RedisFailover without `spec.redis.affinity`.

The default probes are also part of the pod template. The redis pods restart one time when `redis.customLivenessProbe` is not set (#217, #249). With Sentinel enabled, the sentinel pods restart one time when `sentinel.customLivenessProbe` or `sentinel.customReadinessProbe` is not set (#217, #218).

1. List the affected RedisFailovers:

   ```shell
   kubectl get redisfailovers -A -o json | jq -r '.items[]
     | select(
         (.spec.redis.affinity == null)
         or (.spec.redis.securityContext != null and .spec.redis.securityContext.seccompProfile == null)
         or (.spec.sentinel.securityContext != null and .spec.sentinel.securityContext.seccompProfile == null)
         or .spec.redis.customLivenessProbe == null
         or (.spec.sentinel.enabled == true
           and (.spec.sentinel.customLivenessProbe == null or .spec.sentinel.customReadinessProbe == null)))
     | "\(.metadata.namespace)/\(.metadata.name)"'
   ```

2. Plan the upgrade for a time when one failover is acceptable for each of these RedisFailovers. The operator replaces the redis replicas first, one at a time, and waits until each new pod is ready. It replaces the master last:
   - With Sentinel, the operator waits until each Sentinel sees a quorum of replicas. The replacement of the master then starts a Sentinel failover.
   - Without Sentinel, the operator promotes a replica at the next reconcile. Writes fail until then.
   - In bootstrap mode, only the replicas restart.

   Kubernetes replaces the sentinel pods with a rolling update. These changes restart a pod only one time.
3. If a workload cannot run with `RuntimeDefault`, set `seccompProfile` in the `securityContext` of that RedisFailover before the upgrade.

### 2. Remove the command renames that validation rejects

The operator does not reconcile a RedisFailover with a rename of a command that it needs (#248). The status shows `NotHealthy` and the validation error. Without reconciliation, the operator does not move the master label and does not repair a failed master. These renames already broke the RedisFailover, except `ACL` without an `aclfile` and `SAVE`, which validation allows.

1. List the RedisFailovers with such a rename:

   ```shell
   kubectl get redisfailovers -A -o json | jq -r '.items[] | . as $rf
     | select(any(.spec.redis.customCommandRenames[]?.from | ascii_upcase;
         IN("AUTH", "CLIENT", "CONFIG", "INFO", "PING", "PSYNC", "REPLCONF", "REPLICAOF", "SLAVEOF")
         or (. == "ACL" and any($rf.spec.redis.customConfig[]?; ascii_downcase | startswith("aclfile")))
         or (IN("EXEC", "MULTI", "PUBLISH", "SUBSCRIBE") and $rf.spec.sentinel.enabled == true
           and ($rf.spec.bootstrapNode == null or $rf.spec.bootstrapNode.allowSentinels == true))))
     | "\($rf.metadata.namespace)/\($rf.metadata.name)"'
   ```

2. Remove these entries from `spec.redis.customCommandRenames` of each listed RedisFailover. Redis reads `rename-command` only at startup, so the change applies at the next restart of a pod.

### 3. Copy the objects that the operator deletes

The operator deletes the PodDisruptionBudget `rfr-<NAME>` or `rfs-<NAME>` when `disablePodDisruptionBudget` is `true` (#248). An old PodDisruptionBudget blocks the node drains that the flag must permit. The operator also deletes the ServiceAccount `rfs-sa-<NAME>` when `sentinel.serviceAccountName` is set to a different name, and no Sentinel pod uses it. The operator deletes only an object that the RedisFailover owns.

1. If you use one of these objects, copy it under a different name before the upgrade.

### 4. Update a ClusterRole that you maintain yourself

The operator now writes the RedisFailover status through the `status` subresource (#207). This needs `get` and `patch` on `redisfailovers/status`. Without these verbs, the API server refuses each status write.

The ClusterRoles in the Helm chart, in `manifests/kustomize` and in `example/operator` grant these verbs. If you use one of them, go to the next step.

1. Add this rule to your ClusterRole:

   ```yaml
   - apiGroups:
       - databases.spotahome.com
     resources:
       - redisfailovers/status
     verbs:
       - get
       - patch
   ```

2. Optionally, add `delete` on `poddisruptionbudgets` and `serviceaccounts`. Without this verb, the operator logs a warning and keeps the objects from step 3.
3. Apply the ClusterRole before you upgrade the operator.

### 5. Set the image pull Secrets of the Helm chart

Do this step only if you install with Helm and set `imageCredentials.create: true`.

The default of `imageCredentials.existsSecrets` is `[]` (#244). With an empty list, the chart creates a pull Secret from `imageCredentials.registry`, `username` and `password`. If `username` or `password` has the placeholder value, `helm upgrade` stops with an error.

1. If the operator pod pulls with the Secret `registrysecret`, add it to your values:

   ```yaml
   imageCredentials:
     create: true
     existsSecrets:
       - registrysecret
   ```

2. If you want a pull Secret from the chart, set `imageCredentials.registry`, `imageCredentials.username` and `imageCredentials.password`.

### 6. Prepare an install with `redis-operator.yaml` or a kustomize overlay

Do this step only if you install the `redis-operator.yaml` file of the GitHub release, or a kustomize overlay without your own `namespace:`.

The `redis-operator.yaml` file contains the `overlays/default` overlay (#244). The overlays install the operator in the `default` namespace. The ClusterRoleBinding must name the namespace of the ServiceAccount, so the files cannot leave the namespace open.

- `kubectl apply -n <namespace>` does not work with these files. kubectl refuses the namespaced objects, but it applies the ClusterRole and the ClusterRoleBinding.
- The Deployment has a different selector than the `redis-operator.yaml` file of earlier releases. Kubernetes cannot change the selector of a Deployment, so you must delete the old Deployment.
- Run only one operator in a cluster. Each operator takes the leader lease in its own namespace, so two operators in different namespaces both change the RedisFailovers.

1. To install the operator in a namespace other than `default`, write a `kustomization.yaml`:

   ```yaml
   apiVersion: kustomize.config.k8s.io/v1beta1
   kind: Kustomization

   namespace: <namespace>

   resources:
     - github.com/Saremox/redis-operator/manifests/kustomize/overlays/default?ref=<release-tag>
   ```

2. In step 8, delete the old operator Deployment before you apply the new manifests:

   ```shell
   kubectl delete deployment redis-operator -n <old-namespace>
   ```

3. In step 8, apply `redis-operator.yaml`, or your `kustomization.yaml` with `kubectl apply -k <directory>`.

### 7. Find the RedisFailovers that get new Sentinel timeouts

The operator adds `down-after-milliseconds 5000` and `failover-timeout 10000` to the Sentinel `customConfig` when `customConfig` does not set them (#242). Earlier releases added them only to an empty `customConfig`. With other entries, the Sentinels used the built-in values `30000` and `180000`.

The operator applies the new values to the running Sentinels at the next reconcile after the upgrade. The pods do not restart. Sentinel then marks the master as down after 5 seconds without an answer, not after 30 seconds.

1. List the affected RedisFailovers:

   ```shell
   kubectl get redisfailovers -A -o json | jq -r '.items[]
     | select(.spec.sentinel.enabled == true and (.spec.sentinel.customConfig // []) != [])
     | [.spec.sentinel.customConfig[] | split(" ")[0] | ascii_downcase] as $keys
     | select(($keys | index("down-after-milliseconds")) == null or ($keys | index("failover-timeout")) == null)
     | "\(.metadata.namespace)/\(.metadata.name)"'
   ```

2. To keep the built-in values, add `down-after-milliseconds 30000` and `failover-timeout 180000` to `spec.sentinel.customConfig` of these RedisFailovers. Do this before the upgrade. The running Sentinels already use these values, so the change has no effect before the upgrade.

If no RedisFailover is in the list, or the new values are correct for you, go to the next step.

## Upgrade

### 8. Replace the CRD and upgrade the operator together

The CRD enables the `status` subresource (#207). An operator and a CRD from different releases cannot write the status:

- An older operator writes the status through the main resource. The API server ignores these writes with the new CRD.
- The new operator writes the status through the `status` subresource. These writes fail with the old CRD.

The RedisFailovers keep their current status during the upgrade. Do step 8 in one maintenance window, so the time between the CRD and the operator upgrade is short.

Helm does not update the CRD on `helm upgrade`. It installs the CRD only on `helm install`.

1. Set the version:

   ```shell
   REDIS_OPERATOR_VERSION=<release-tag>
   ```

2. Replace the CRD:

   ```shell
   kubectl replace -f https://raw.githubusercontent.com/Saremox/redis-operator/${REDIS_OPERATOR_VERSION}/manifests/databases.spotahome.com_redisfailovers.yaml
   ```

   If you set `crds.upgradeHook.enabled: true` in the chart values, a Helm hook applies the CRD before the operator upgrade. In that case, do not do this step.

3. Upgrade the operator immediately:

   ```shell
   helm upgrade redis-operator redis-operator/redis-operator --version ${REDIS_OPERATOR_VERSION}
   ```

   If you install with kubectl or kustomize, apply the operator manifests of the same release. Step 6 gives the order.

### 9. Apply the RedisFailovers with new fields again

The old CRD had the schema of an older k8s.io/api. The new CRD has the schema of k8s.io/api 0.37 (#208). The API server removes fields that the CRD schema does not know, and it does not show an error. With the old CRD, the API server removed fields such as `httpGet.protocol`, `grpc.mode` and `volumeMounts[].bindMountOptions` from the stored RedisFailovers. The new CRD does not restore these fields.

1. Find the RedisFailover manifests that set one of the new fields.
2. Apply these manifests again after step 8.

If no RedisFailover sets one of these fields, go to the next step.

## After the upgrade

### 10. Make sure that the upgrade is correct

1. Make sure that the CRD has the `status` subresource:

   ```shell
   kubectl get crd redisfailovers.databases.spotahome.com \
     -o jsonpath='{.spec.versions[?(@.name=="v1")].subresources}'
   ```

   The output is `{"status":{}}`.

2. Make sure that the operator log has no errors for status writes. An error with `forbidden` and `redisfailovers/status` tells you that a ClusterRole does not have the verbs from step 4.
3. Make sure that each RedisFailover has the state `Healthy` after the pods restart:

   ```shell
   kubectl get redisfailovers -A \
     -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,STATE:.status.state'
   ```

4. Make sure that only one operator Deployment exists:

   ```shell
   kubectl get deployments -A -l app.kubernetes.io/name=redis-operator
   ```

5. For each RedisFailover from step 7, make sure that the Sentinels use the timeouts that you expect:

   ```shell
   kubectl exec -n <namespace> deploy/rfs-<name> -c sentinel -- \
     redis-cli -p 26379 SENTINEL MASTER mymaster | grep -A1 -E '^(down-after-milliseconds|failover-timeout)$'
   ```
